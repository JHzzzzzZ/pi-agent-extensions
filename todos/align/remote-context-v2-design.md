# 共享设计：远端上下文协议 v2（`dir-context#8`/`#9` + `remote-tools#13`/`#14` 共用一个协议修订）

- 日期：2026-10-11（UTC）· 参与：用户（真机实测挖出 `#9`/`#13`/`#14`，并选定「四件打包一个分支」）+ agent（设计）
- 本文件是四份对齐文档的共同设计来源。**它不是对齐门的目标文件**——门只校验派生的 `todos/align/<名>#<id>.md`。

## 为什么四件必须同一批

四处改动落在**同一份线格式与同两个模块**上：

| 条目 | 要动的东西 |
|---|---|
| `remote-tools#13`（p5） | 分帧格式本身（NUL 分帧可被内容伪造） |
| `remote-tools#14` | 路径的归一化（去重键 + 块标题） |
| `dir-context#9` | 「空内容算不算东西」的判定 |
| `dir-context#8` | 读不出的**错误码**（消费方按码选提示） |

`#13` 必须先改线格式，`#14`/`#8` 都要动同一段拼装与解析代码；分四次做等于同一份代码改四遍、跑四轮评审。

## 线格式 v2

提供方一趟 ssh 的 stdout，帧的重复结构：

```
frame  := MARK <path> \0 <payload> \0
MARK   := \x01  读得出     payload = 文件内容的 base64（允许换行包裹；解码前剥空白）
        | \x02  存在但读不出  payload 恒为空，path 仍照实给
        | \x03  远端环境不支持（转义工具缺失）——单帧，无 path 无 payload
```

**为什么不沿用 v1 的裸 NUL 分帧**：v1 把「NUL 不会出现在文本内容里」写成了契约，而这只对纯文本成立。内容含 NUL 时，NUL 被当成分帧边界 ⇒ **内容可以伪造出路径帧**。`#13` 的真机实测：`AGENTS.md` 内容 `FIRST\0/evil\0SECOND` ⇒ 注入出 `Loaded …:/evil`（该文件不存在），真内容被劈成两半错配。

base64 的字母表（`A–Za–z0–9+/=` 与空白）**不含 NUL / SOH / STX**，于是「每个 NUL 分隔段都是一个完整帧」重新成立，内容再也无法伪造边界。代价是线上体积 +33%（一趟 ssh，可忽略）。

**通道名升 v2**：`pi-extensions:dir-context-remote-context:v1` → `…:v2`。新旧版本不匹配 ⇒ 没有提供方 ⇒ 走既有的 `unavailable` 提示行（fail-closed），**不会**把 v1 的输出按 v2 误解析。

**`\x03` 的意义**：`base64` 缺失时 `base64 < "$f"` 只往 stderr 报错、stdout 什么都不出，那样会得到「空 payload ⇒ 看起来像空文件 ⇒ 静默跳过」。所以命令开头加一次 `command -v base64` 探测，缺失就发 `\x03` ⇒ 提供方回 `ok:false`（宁可提示，不静默）。

## 路径归一化

解析出远端绝对路径后**立刻** `posix.normalize`，再用于 ① 祖先链遍历 ② 帧里的 `<path>`。消费方的去重键与块标题都取自帧里的路径，因此一处归一化同时修好两边：`/tmp/dcB/../dcB/x.txt` 不再产出新键、不再重复注入，标题也不会带 `..`。

## 空内容

**提供方照实上报**（0 字节文件就是「一个内容为空的文件」——诚实是它的职责，它不做注入决策）；**消费方判定**「空 ⇒ 没有可注入的新内容」⇒ 归 `nothing`：不注入空块、不标记已注入、不出提示。因为没标记，文件后来有内容时同一会话再触碰即可拿到。

## 错误码

读不出不再复用通用 `REMOTE_CONTEXT_FAILED`，改专属 `REMOTE_CONTEXT_UNREADABLE`；消费方按码挑**静态**提示常量——不插值 host 或路径（既有口径：host 也是模型输入）。

## 明确不做

- **不保留 v1 兼容层**：同仓同 push，通道名版本已足够 fail-closed；写双解析器是没必要的复杂度。
- **不改「空内容也要上报」的提供方语义**（虽然消费方会跳过它）——保持「提供方只取、消费方只判」的分工不动摇。
- **不做远端内容的语义/大小过滤**（阈值、类型判断等），只做协议层与判定层的修正。
