## 意图

用户报障：通知里的「日志: <path>」看起来没有对应的日志。真机复现出**两个独立缺陷**（都不是「结束时不写盘」——本机两次实测日志内容完整）：

**缺陷 ①：日志串味（id 复用 + append）**

- 事实：`jobSeq` 是**实例内**计数器（`index.ts`），`/reload` 后新实例从 `bg-1` 重新编号；日志以 `flags: "a"`（append）打开（`shell-ops.ts`、`remote-tools/ops.ts`）。
- 复现（2026-12-12）：reload 后新 job 拿到 `bg-1`，写进**已存在的** `bg-jobs/35036/bg-1.log`（上个实例同名 job 的 182 字节输出）→ 文件 209 字节 = 旧输出 + 本次输出；通知的「末尾输出」把两条命令混在一起。
- 危害：排查时读到别的命令的输出；模型收到与本次命令无关的文本。

**缺陷 ②：通知路径死链（prune 的策略与「每条命令一格」叠加）**

- 事实：保留策略 = 最多 50 个文件 / 7 天，**只在 `session_start` 执行**（`index.ts` 唯一调用点），且**跨会话目录**统一取最新 50；而**每条命令（含前台）都会建一个日志文件**（`shell-ops.ts` 里 `newJobId` + `createWriteStream` 在任何模式判断之前，这是「超时那一刻要有完整历史」的设计代价）。
- 复现（2026-12-12）：`bg-37` 的通知 16:05 到达，16:10 用户 `/reload` 触发 prune → `bg-4..bg-61` 整段被删（目录里只剩「最新 50 个」`bg-62..bg-111`）；通知里的路径成了死链。
- 危害：会话还活着，但通知指向的日志没了；`/bg` 列表在 reload 后也已重置（看不到旧 job）。

## 范围

**做什么**

1. **编号起点取现有日志的最大号 + 1**（`logs.ts` 新增 `nextJobSeq(logRoot)`：读 `<logRoot>/<pi pid>/`，解析 `bg-<n>.log` 取 max；目录不存在/无匹配 → 1）。`index.ts` 的 `newJobId` 改为**懒初始化**：首次分配前扫一次，之后实例内递增。保持 `bg-N` 短 id 形态与 `/bg:kill bg-N` 用法不变。
2. **prune 豁免活着的会话目录的数量上限**（`pruneJobLogs` 增 `options.isAlive`，默认 `isProcessAlive` = `kill(pid, 0)`）：目录名是 pid 且进程还活着 ⇒ 该目录只受 7 天保留期约束、不被 50 上限删；死会话目录照旧按 50 / 7 天清。
   **首轮评审 P1 修正**：豁免必须按「进程是否活着」判，不能只看「是不是自己的目录」——并发的第二个 pi（另一终端 / `pi --print` / 子 agent，同样加载本扩展、共享同一个 `bg-jobs`）在它自己的 `session_start` 里会把**活着的我们**当成「别家目录」按 50 上限删。理由：通知里的路径只有在会话还活着时才有人用，而每条命令（含前台）都占一格。
3. **测试**（同一变更内）：
   - `nextJobSeq`：空目录 → 1；含 `bg-1`/`bg-3` → 4；忽略非 `bg-N.log` 名字；目录缺失 → 1。
   - **伪 reload 集成测试**（`test/index.test.ts`）：预置 `<logRoot>/<pid>/bg-1.log` 写「旧内容」→ 起新实例跑一条前台命令 ⇒ 新 job 编号是 `bg-2`（不是 bg-1），且 `bg-1.log` 内容仍是旧内容（不被写脏）。
   - `pruneJobLogs` 的 `keepDir`：本会话目录文件超上限不被删、别的目录被删；本会话目录里超保留期的文件**仍然**被删。
4. 文档同步：`docs/extensions/timeout-bg.md` 的日志布局/保留策略不变量与新 id 语义（含「为什么不是 wx 重试」的理由）、扩展 `README.md`、根 `README.md` 相关行；扩展 bump 版本。

**明确不做什么**

- 不改 `bg-N` id 形态（不加实例前缀/时间戳）——短 id 是人机共用面，保持稳定。
- 不用 `flags: "wx"` + 重试：同一 pid 目录只属一个进程、实例内编号是顺序分配的，扫一次即无竞争；`wx` 只会在「文件意外存在」时把命令直接打挂（fail-closed 过度）。
- 不给前台命令免建日志（那会丢掉「超时那一刻的完整历史」，是 #1 的既有取舍）。
- 不提高全局 50 上限、不改 7 天保留期。
- 不做跨会话的 job 面（`/bg` 仍只看本会话）——那是另一个量级的需求，不在本次「修缺陷」范围。

## 验收标准

1. **串味消失**：伪 reload 集成测试绿——新实例首个 job 编号 = 现有最大号 + 1，旧文件内容一字节不变；真机：reload 后跑 `run_in_background`，通知的「末尾输出」只有本次命令的输出。
2. **路径不再被自己（或并发的另一个 pi）删**：`pruneJobLogs({ isAlive })` 语义测试绿（活目录不吃上限、保留期仍生效、死目录照旧）；真机：reload 两次后，早先通知里的日志路径仍存在（除非已过 7 天）。
3. **零回归**：timeout-bg 既有 70 个用例全绿 + `npm run typecheck` 零错误；远端 job 的 id/日志走同一号段（`shell-job-host` 的 `allocate` 复用同一个 `newJobId`）。
4. 全量测试门（根 `npm run test:all`）+ 跨厂商单轮评审（T2 口径，reviewer 显式回答「有无首轮未覆盖的行为面疑虑」）。
