# 对齐：dir-context-todo#8 — 远端「读不出（权限）」的诊断到不了使用者

## 意图

`#7` 的评审第 1 轮 P2（reviewer = `kimi-coding/k3-256k`）：提供方**已经能**区分「读不出」与「不存在」（`ok:false` + 专属 message），但消费方把三种 `unavailable` 统一收敛成同一条通用提示（且每会话只一次）⇒

1. **没装 remote-tools**（没有提供方）
2. **ssh 挂了 / 超时 / 非零退出**
3. **约定文件存在但读不出（权限）** ← 用户 `#7` 的实测场景

……这三者对使用者同形。看到「取不到远端上下文」的人不知道该去修权限。

## 范围

**做什么**（共享设计见 `todos/align/remote-context-v2-design.md`）

1. **提供方**：读不出的情形不再复用通用 `REMOTE_CONTEXT_FAILED`，改专属错误码 `REMOTE_CONTEXT_UNREADABLE`（`remote-tools/errors.ts` 的单源表 + 契约卡）。
2. **消费方**：按**错误码**（不是按 message 文本）挑提示常量 ⇒ 读不出时给一条专属静态提示，其余失败仍走既有通用提示。
3. **文案保持静态**：不插值 host、不插值路径（既有口径：host 也是模型输入）；提示条数仍按「每会话每种原因一次」计，不因此变成刷屏。
4. **契约卡**：结果形状表加 `REMOTE_CONTEXT_UNREADABLE` 一行；`docs/extensions/dir-context.md` 与 `docs/extensions/remote-tools.md` 同步。
5. 测试：提供方按码回来（单测）；消费方按码选提示（宿主级用例）。

**明确不做什么**（这是 (A) 相对 (B) 的核心取舍）

- **不摘要/透传提供方的 message 文本**（那是 (B)）：消费方不该依赖另一个扩展的文案字符串，否则两边要一直手动对齐。
- 不新增提示渠道（不弹窗、不进 widget）——仍是一行会话内提示。
- 不做错误堆栈/原因链展示；使用者只需要知道「去修权限」。

## 验收标准

1. **三态可区分**（条目原文的验收口径）：在真实会话里，「没装 remote-tools」「ssh 失败」「读不出」三种情形给出的提示**不是同一条**（前两者可共用通用提示，后者必须是专属文案）。
2. **按码不按文案**：消费方的分支只看错误码；把提供方 message 改成任意文本，行为不变（单测锁定）。
3. **仍是静态模板**：提示常量里没有任何插值点（单测断言常量无占位符）。
4. **每会话一种原因一次**：同一种原因连续出现只提示一次；不同原因各自的一次互不吞掉。
5. **失败不打断**：提示照旧不改变工具结果、不进上下文（沿用既有不变量）。
6. 单测 + typecheck 双绿；全仓 `test:all` 除已知并发抖动外全绿。
7. 真机对照：真实 `pi` + 真实 ssh，造 `chmod 000` 场景 ⇒ 看到的是**权限专属**提示（与「远端没有约定文件」的静默、与「没装 remote-tools」的通用提示都不同）。
8. 跨厂商独立评审（红线 11）逐条处理到某轮无新意见。
