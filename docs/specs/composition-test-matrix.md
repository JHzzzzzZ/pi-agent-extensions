# 规格：插件组合集成测试矩阵（A+B 兼容 / A、B 独立）

- 来源：`todos/align/general-todo#32.md`（对齐已确认，2026-10-11）· 条目 `general-todo#32` · 分支 `feat/composition-test-matrix`
- 范围：仓库级测试基础设施（跨扩展），不改任何插件的运行时行为

## Problem Statement

插件已 17 个，但它们只在真实 pi 会话里一起跑过，没有人验证过任意两两组合。两类问题因此只能撞运气发现：

- **A+B 同装出事**：两个插件写同一个槽位（状态键、widget、内置工具面、宿主事件钩子）而互相覆盖；或跨扩展能力协商（`pi.events` 频道）两边假设不一致。历史事故：`widget-band` 沉底、pwr 缺 `revive()` 导致 `/new` 之后永久抛错。
- **A 单装出事**：B 不在时，A 拿不到对方的频道/工具，行为进入未声明的分支（崩、或静默做错事）。而"单装"恰恰是用户最常见的用法——只装自己需要的插件。

现有资产只覆盖了零星几对：`jev-safe-gate/test/solo-gate.test.ts`、`remote-tools/test/capability.test.ts`、`remote-tools/test/shell-composition.test.ts`、`timeout-bg/test/index.test.ts`。`tools/install-smoke.mjs` 只证明"17 个能一起加载"，不验证组合语义。`docs/cross/` 六份契约卡说了规则，**但没有任何一处说清"谁占了哪个槽"**，所以冲突既无法预测也无法回归。

## Solution

给仓库加一层**组合测试矩阵**，由一份"接触面清单"驱动，三层验证：

1. **接触面清单（单源）**：`docs/cross/composition-surfaces.md` 逐插件声明占用的槽位（状态键 / widget / 工具与内置工具面 / events 广播与订阅 / 宿主事件钩子 / 模型面 / 命令与快捷键 / 文件契约）、独占或替换关系（`独占声明`）与可共享关系（`共享槽`）。
2. **校验器**：`tools/composition-surfaces.mjs` 保证清单完备（每个扩展目录都出现）、声明有效（写下的键能在源码里找到）、并**生成 L2 配对集合**（按共享接触面取交集，不做 18²）。
3. **三层测试**：L1 单装（每个插件独立加载）、L2 配对（按交集生成的每一对同装）、L3 关键组合端到端（真 pi 子进程 + 真模型，opt-in）。L1/L2 离线进 `npm run test:all`。

判据明确到可执行：**兼容** = 双方注册成功、同槽按声明裁决、加载顺序无关、卸载/重载无残留；**独立** = 单独加载不抛未捕获异常、注册面自洽（注册的都在清单里、声明的都真注册）。

## User Stories

1. 作为插件作者，我想在新增一个扩展后立刻知道它和谁共享槽位，这样我不用靠真机会话撞 bug。
2. 作为插件作者，我想让"漏在清单里声明接触面"直接报错，这样新插件不会静默逃过矩阵。
3. 作为插件作者，我想让矩阵自动把新插件和所有共享接触面的老插件配成对来跑，这样我不用手工维护组合列表。
4. 作为插件作者，我想在同装测试里看到"谁写进了同一个槽、按什么规则裁决"，这样我能判断是设计冲突还是实现 bug。
5. 作为插件作者，我想让"先 A 后 B"和"先 B 后 A"跑出同一结果，这样加载顺序不会成为隐藏契约。
6. 作为插件作者，我想让卸载/重载后状态干净可重入（对齐 pwr `revive()` 教训），这样 `/new`、`/reload` 之后的组合行为不会永久坏掉。
7. 作为用户，我想单独装一个插件就能正常工作，这样我不必为了装 A 而被迫装 B。
8. 作为用户，我想知道某个插件在缺少搭档时的实际行为，这样我遇到异常行为时知道是不是缺插件（本变更交付的是 L1 的「独立加载不抛错 + 注册面自洽」；按扩展的降级语义（fail-closed / fail-soft）**逐条声明**与断言见收尾备注，尚未实现）。
9. 作为用户，我想让关键组合（远端超时转后台、免审批与危险门、目录上下文与内置工具面、pwr 与内置工具钩子）有端到端用例，这样最常用的搭配有真机保障。
10. 作为维护者，我想让矩阵在自己的 CI/本地门里离线跑完（无网络、无鉴权），这样每次提交都能跑。
11. 作为维护者，我想让矩阵"能抓到真冲突"被变异用例证明过（注入假冲突必须报红），这样它不会退化成纸面绿。
12. 作为维护者，我想让矩阵至少覆盖现有的 4 个跨扩展测试所覆盖的组合，这样自动化不会比人工现状更弱。
13. 作为维护者，我想让矩阵单套件跑得快（墙钟预算有上限），这样它不会被从总门里摘掉。
14. 作为维护者，我想让接触面清单成为"谁占了哪个槽"的唯一去处，这样我不会在六份契约卡之间找一个不存在的事实。
15. 作为新加入的人，我想通过清单一眼看懂 17 个插件在哪些共享面上互相影响，这样我不用读完 17 份 README 才知道系统怎么拼起来。

## Implementation Decisions

**清单格式与语义（`docs/cross/composition-surfaces.md`）**

- 每个插件一节，节内为固定键的行式声明（`键: 值`），机器可解析、人可以读：
  - `状态键` / `widget` / `工具` / `工具面`（`replace:<内置工具>` 或 `wrap:<内置工具>`）/ `events 广播` / `events 订阅` / `宿主钩子` / `模型面` / `文件契约` / `命令` / `快捷键`
  - `独占声明`：与他人在同一槽取值上的 owner 主张（例：timeout-bg 主张 `replace:bash`）
  - `共享槽`：该取值可多方共享并写明共享契约（例：`widget-band` 排序带的段键顺序）
  - `模式`：加载期面随运行模式分叉（如 agent-team 的 cockpit / leader）
- 无任何注册面的插件显式写 `无`（不省略整节）——"没声明"与"声明为空"必须可区分。

**校验器（`tools/composition-surfaces.mjs`）**

- 导出纯函数（解析清单、算接触面交集、生成配对集合、做正向校验），CLI 只在直接执行时跑；命令面：`--check`（默认，校验完备性与声明有效性）、`--pairs`（打印生成的配对集合）、`--json`。
- 三种 fail-closed 错误：扩展目录未在清单出现（报目录名 + 修法一行）、声明的键在源码中找不到、清单里出现不存在的扩展目录。退出码：0 通过 / 1 校验失败 / 2 用法错误。
- 配对规则：两插件在任一接触面维度上取值相交（含"一个提供、另一个消费同名 events"）即配对；同槽但两侧都无 `独占声明` 属真冲突，交给 L2 用例报错。
- 正向校验是"文档声明 → 源码存在"的单向检查，**不做**源码 → 文档的自动提取（实测正则提取会漏 `pi.registerTool` 名与 `registerVirtualModel`，不可靠）。

**测试套件（根 `test/`）**

- `test/composition-standalone.test.ts`（L1）：每个插件单独加载，断言无未捕获异常、生命周期可重入、注册面自洽（注册面 ⊆ 声明、声明面 ⊆ 观测，含状态键 / widget / 钩子 / 命令 / 快捷键）。
- `test/composition-pairs.test.ts`（L2）：对校验器生成的每一对同装，断言兼容四条（注册成功、同槽按声明裁决、加载顺序无关、卸载/重载无残留），并对每一对跑两个加载顺序。
- 两者共用一个小工具模块（假宿主 `ctx`、事件总线、状态/widget 槽记录器），放在根 `test/` 下，避免复制粘贴。
- `tools/test-all.mjs` 的 `DEFAULT_SUITES` 增加 `root:composition` 条目（cwd = 仓库根），`test/test-all.test.ts` 的覆盖锁定测试同步。

**独占与冲突语义（D6）**

- 允许声明独占/替换关系；同装时按声明断言 owner / 消费者 / 短路行为。
- 未声明而真冲突 ⇒ 测试失败（fail-closed）。**不引入"禁止同装"档**——用户要的是 A+B 能一起跑。

**L3 关键组合（白名单，opt-in）**

- `remote-tools × timeout-bg`（远端超时转后台）、`jev-safe-gate × solo-mode`、`dir-context × 内置 read/write/edit`、`pwr × 内置 tool_call`。
- 走真实 pi 子进程 + 临时配置目录（沿用 `tools/install-smoke.mjs` 的手法），需要真模型时以环境变量 opt-in，未设目标一律 `skip`（不静默绿）。

**文档与登记**

- `docs/INDEX.md` 路由新卡与新套件；根 `README.md` 更新测试数（唯一来源）；`docs/tools/` 增校验器用法卡。

## Testing Decisions

- **只测外部行为**：断言落在"宿主可见的注册面与可观测状态"（注册的事件名与键、状态/widget 写入、能力频道读写、错误码），不断言插件内部函数调用序列。
- **seam 选最高且已有先例的那个**：真实 `ExtensionRunner` + 真实事件总线（同进程），先例是 `src/extensions/dir-context/test/index-host.test.ts` 与 `src/extensions/jev-safe-gate/test/index-host.test.ts`——它们已经证明这条 seam 能抓住纯函数测不出的真 bug。不新造 seam、不改插件去迎合测试。
- **离线性**：L1/L2 无网络、无鉴权、无 npm 依赖（沿用 `node:test` + 手写 fake 的口径）；只有 L3 需要真 pi 与真模型。
- **变异自证**：L2 内含一个"注入假同槽冲突必须报红"的用例——矩阵自身的有效性也被测试锁定。
- **不得比人工现状弱**：L2 生成的配对集合必须包含现有 4 个跨扩展测试覆盖的 4 对（用断言锁定，不是靠人记得）。
- **性能门**：单套件墙钟上限（参考 60s），超限即按接触面分组拆成多套件，而不是删用例。

## Out of Scope

- 不改任何插件的运行时行为与既有契约（矩阵首跑若抓到真冲突，另开条目处理）。
- 不做 18² 全量组合，不追求穷尽；只跑共享接触面的对。
- 不自动从源码提取接触面（只做"声明 → 源码存在"的单向校验）。
- 不打宿主补丁、不引入 npm 依赖、不引入测试框架。
- L3 不进 CI 必跑门（真模型成本）。
- 不把 `docs/cross/` 既有六份契约卡的内容复制进新清单；清单只回答"谁占了哪个槽"，细节仍指向既有卡。
