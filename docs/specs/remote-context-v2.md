## 问题陈述

`dir-context` 的远端目录自动注入（`#6`）与「读不出不再静默」的修复（`#7`）上线后，用户按真实触发条件做真机复验，又挖出四个缺陷。它们共同的形状是：**把不可信输入当成了可信**，或者**把该说的话咽了回去**。

1. **分帧可被内容伪造**（`remote-tools#13`，最重）。线格式是 `<路径>\0<内容>\0` 重复，而实现里把「NUL 不会出现在文本内容里」写成了契约。文件内容含 NUL 时（`FIRST\0/evil\0SECOND`），NUL 就成了帧边界：读一个文件能注入出**多个**块，其中一个的标题是不存在的 `/evil`，真内容被劈成两半错配。这不是显示问题——远端任何写文件的进程都能往模型上下文里塞伪装成「另一份约定文件」的文本。
2. **同一份文件被重复注入**（`remote-tools#14`）。去重键与块标题用未归一化的路径，`/tmp/dcB/x.txt` 与 `/tmp/dcB/../dcB/x.txt` 是两个键 ⇒ 第二次再注入一份，标题还带着 `..`。
3. **0 字节文件注入空块并误标记**（`dir-context#9`）。`#7` 的同构另一半：症状一样（空块 + 抑制 + 误标记），触发条件从「读不出」换成「真的空」。`#7` 的对齐文档里我明确保留了这条行为，本条目推翻它。
4. **「读不出」的诊断到不了使用者**（`dir-context#8`，`#7` 评审第 1 轮 P2）。提供方能区分，消费方把三种 `unavailable` 收敛成同一条通用提示 ⇒「没装 remote-tools」「ssh 挂了」「权限坏了」对使用者同形，看到提示的人不知道该去修权限。

**为什么四件一次做完**：四处落在同一份线格式与同两个模块上（`remote-tools/context.ts` 的帧构造/解析、`dir-context/index.ts` 的消费判定）。`#13` 必须改线格式，`#14`/`#8` 都要动同一段代码；分四次做等于同一份代码改四遍、跑四轮评审。

## 方案

### 线格式 v2

```
frame := MARK <path> \0 <payload> \0
MARK  := \x01 读得出      payload = 文件内容的 base64
       | \x02 存在但读不出  payload 恒为空
       | \x03 远端环境不支持 单帧，无 path 无 payload
```

- **为什么 base64**：base64 的字母表（`A–Za–z0–9+/=` 与空白）不含 NUL / SOH / STX ⇒「每个 NUL 分隔段都是一个完整帧」重新成立，**内容无法参与帧边界判定**。代价是线上体积 +33%（一趟 ssh，可忽略）。真机验证：含 NUL / 制表 / CRLF / 中文的文件往返 byte-for-byte 一致。
- **为什么每帧带标记**：v1 靠「路径以 `/` 开头」判是不是路径帧，而读不出时那一级什么都不发 ⇒ 与「没有约定文件」同形。标记让「读得出 / 读不出 / 不支持」三态在协议层可区分。
- **为什么有 `\x03`**：远端若没有 `base64`，`base64 < "$f"` 只往 stderr 报错、stdout 什么都不出 ⇒ 会得到「空载荷 ⇒ 看起来像空文件 ⇒ 静默跳过」。所以远程先探一次 `command -v base64`。
- **通道名升 v2**（`pi-extensions:dir-context-remote-context:v2`）：新旧不匹配 ⇒ 没有提供方 ⇒ 走既有提示行（fail-closed），不会把 v1 的输出按 v2 误解析。不写双解析器。

### 路径归一化

解析出远端绝对路径后立刻 `posix.normalize`，再用于①祖先链遍历②帧里的 `<path>`。消费方的去重键与块标题都取自帧里的路径 ⇒ 提供方一处归一同时修好两边。**不做**符号链接同文件识别（那需要 `realpath`，判据是「路径字符串归一」而非「文件身份」）。

### 空内容

提供方**照实上报**「0 字节文件 + 空内容」（「取」是它的职责，它不做注入决策）；**消费方**判定「空 ⇒ 没有可注入的新内容」⇒ 归 `nothing`：不注入空块、不标记已注入、不出提示。因为没标记，文件后来有内容时**同一会话**再触碰即可拿到。

### 读不出的专属错误码

`REMOTE_CONTEXT_UNREADABLE`（与通用 `REMOTE_CONTEXT_FAILED` 并列，值由契约固定）。消费方**按码**挑提示常量，不摘要对端 message（否则两边要一直手动对齐文案）。未知码回落通用提示（前向兼容）。两种提示都保持**静态**（不插值 host / 路径——host 也是模型输入），且**按原因各记一次**（一种原因出现过不挡另一种）。

## 用户故事

- 作为**使用远端约定文件的开发者**：远端某级 `AGENTS.md` 权限坏了，我看到的是一句「存在但读不出（权限）」，而不是「远端没有约定文件」的沉默——我知道去 chmod。
- 作为**同一会话里修好了权限的人**：修完再触碰，内容立刻进来，不用重开会话。
- 作为**往约定文件里贴了奇怪二进制内容的人**：注入的就是那个文件本身，不会多出别的路径的块，也不会少一半。
- 作为**用 `..` 写路径的模型/脚本**：同一份文件只注入一次，标题是真实路径。
- 作为**把 `AGENTS.md` 建空占位的人**：先不注入任何东西（空块是噪声），等我写进内容后同一会话就能拿到。

## 实现决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 内容编码 | base64（`base64 < "$f"`，解码前剥空白） | 唯一能保证「载荷不含帧分隔字节」的简单办法；GNU/BSD/busybox 都有，`-w0` 不需要（换行包裹剥掉即可） |
| 标记字节 | `\x01`/`\x02`/`\x03` | 均可打印字符之外、base64 字母表之外 |
| 归一位置 | 只在提供方一处 | 消费方的键与标题都取自帧里的路径；两边都归一反而让「谁负责」模糊 |
| 空内容判定位置 | 只在消费方 | 沿用 `#6` 的分工：提供方只取、消费方只判 |
| 错误码判定 | 只看码、不摘要 message | 消费方不该依赖另一个扩展的文案字符串 |
| v1 兼容 | 不保留 | 同仓同 push；通道名版本已 fail-closed |

## 测试决策

- **真 shell 往返是主力**（`test/context-v2.test.ts`）：真的起 `bash -c` 跑 `buildContextCommand` 的输出，再按协议解回来，断言「含 NUL 的内容只产出一个帧」「字节级还原」「`\x02`/`\x03` 帧的样子」。纸面断言（「命令里含 base64」）测不出真 shell 里 `printf`/`base64`/重定向长什么样。平台缺 `bash`/`base64` 时 `skip`。
- **协议形状与归一化**：纯本地，ssh 边界注入手写 fake。
- **消费侧宿主级**（`dir-context/test/index-host.test.ts`，真实 `ExtensionRunner`）：空内容 ⇒ 不追加块、不写状态、不出提示，且随后有内容时可注入；按码分流（`REMOTE_CONTEXT_UNREADABLE` ⇒ 权限文案、未知码 ⇒ 通用文案、对端 message 不出现）；按原因各一次。
- **变异验证**（6 个变异逐个注入，全部被测出）：分帧退回 v1、去掉归一、不认 `\x03`、读不出复用通用码、不过滤空内容、消费方不看错误码。
- **真机验收**（真实 pi + 真实 ssh 到本机 WSL，6/6）：伪造不可达 / 真内容仍在 / 别名不重复注入 / 空文件不注入空块 / 写入后同会话拿到 / 权限专属提示。

## 范围外

- 不做远端内容的语义过滤（大小阈值、类型判断）——只修协议与判定。
- 不做符号链接同文件识别。
- 不改**本地**（非远端）路径对 0 字节约定文件的既有行为；若本地也有同款问题，另立条目。
- 不做 v1 兼容解析层。
