# todo 依赖门：`dependsOn` 引用 + `aligned → processing` 前 fail-closed

Status: accepted（2026-09-14，todo-cli-todo:10；用户逐条采纳第一轮 Q1–Q6）

条目文本三言两语，「A 的开工前提是 B 完成」这类约束此前只活在人的记忆与注记里：B 没落地就开了 A 的工，返工发生在最贵的时候。决定：条目新增原生字段 `dependsOn: string[]`（规范化引用 `文件基名#id`，允许跨文件），并在 ADR-0003 预留的插位（第二次 `claim`，`aligned → processing`）前做依赖门——存在未完成（`status !== done`）依赖时 fail-closed 拒绝开工，逐条列出等待对象与状态。写路径（`add --dep` / `dep add`）拒绝悬空引用、自引用与成环（回显环路径），`lint` 另做全量扫描兜住合并产物。schema 升 v3：写出必填、读 v1/v2 归一为空数组、不回填。「取消/搁置」不新增状态——`complete` 一律 `done`，依赖机械解锁，但输出一行提示反查直接依赖者，逼人重新判断 A 的前提是否仍成立。

## Considered Options

- **只允许同文件数值 id**：引用短、无跨文件歧义，但本次工作区里真实依赖经常跨插件文件（`general-todo#11` 这类），写不进就退化成注记——否决。
- **跨文件但保留 `文件#id` 短名与全名两种存储形态**：读起来省字，但同一引用两种写法会分裂查重、环检测与 lint 的口径——否决（输入可宽松、存储必须归一）。
- **悬空引用放行（指向「计划中、尚未登记」的条目）**：让「先写依赖再补条目」顺手，但错拼的引用会静默存活，等开工时才发现等错了对象——否决。
- **只拦 `claim`、不改任何展示**：改动面最小，但 agent 盘点时看不到「哪条 aligned 现在开不了工」，被阻塞条目会反复撞门——否决（改 `list`/`triage`，但不动 `summary` 与非阻塞条目的输出字节）。
- **环只在 `lint` 报，写路径放行**：环能被发现，但发现得太晚（登记时人不在场，lint 也不在每次写路径上）——否决，改双保险：写路径拒绝 + lint 全量兜底。
- **留 schema v2、`dependsOn` 可选缺省 `[]`**：省一次版本升级，但同一 version 里字段时有时无，与 v2（`alignedAt` 必填）的先例分叉——否决。
- **新增第六态表达「已取消」**：语义更准，但状态机、迁移表、展示、迁移器全线扩张，与本条目标（依赖门）不同量级——否决，推迟到独立需求；本次用 `complete` 提示行兜住风险。
- **阻塞影响排序（blocked 沉底）**：一眼看到能开工的，但排序是 `list` 的稳定契约，沉底会与既有输出习惯和测试冲突——否决。

## Consequences

- schema v3：条目新增 `dependsOn: string[]`；读接受 `version: 1|2|3` 并归一（旧版缺字段 → `[]`），写出一律 v3；任一写操作即整文件升版，不做批量回填。
- 命令面 8 → 9 子命令：新增 `dep`（`add` / `remove`），`add` 增 `--dep`；`docs/tools/todo-cli.md` 的「命令面冻结」不变量按本条更新口径（改为「命令面版本化」，变更须同变更内同步 USAGE/卡/SKILL.md）。
- 门的插位与语义：唯一硬门是第二次 `claim`；首次 `claim`（`open → aligning`）与 `align` 不受依赖约束——被阻塞条目可以先对齐、先写文档再排队等前提。
- 回滚边界：旧版 CLI 读 v3 文件明确报错；回滚 = git 历史 + `migrate to-md`（与 v2 时一致）。
- 悬空不放行 ⇒ 在落后于主干的 worktree 里声明「主干刚登记的目标」会被拒绝，须先同步分支——可接受，宁可拒绝也不写错引用。
- 「取消即解锁」是机械语义：被取消的依赖同样解锁下游。风险由 `complete` 的提示行（列出直接依赖者）+ 人工重新对齐承担，不加状态、不加旁路。
- 依赖只是台账内引用，不跨仓库、不做传递展开、不做自动等待/自动 claim。
